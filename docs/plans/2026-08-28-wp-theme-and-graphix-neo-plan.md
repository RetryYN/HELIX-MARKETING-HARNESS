# 企画書: HELIX-WP-THEME と GRAPHIX-NEO の役割分担（2026-08-28 起案）

status: draft（PO 判断待ち）
owner: PO
related: `base/wp-theme`（HELIX-WP-THEME）、`RetryYN/GRAPHIX-NEO`（企画・要求・PoC）

## 1. 一言で

- **HELIX-WP-THEME** = 「AI と WP 編集の楽しさ」を体験する自由なテーマ。運用知見と開発知見をためる場。
- **GRAPHIX-NEO** = WP-THEME で良かったパターンだけを持ち込み、**AIO / LLMO（AI 検索・LLM 引用への最適化）**を本気で取りにいく製品。

WP-THEME は「広く試して学ぶ」、GRAPHIX-NEO は「絞って勝つ」。同じ 4 層モデル（トークン → 骨格 → パーツ → 内容）の上に載せ、パターンは WP-THEME から GRAPHIX-NEO へ一方向に昇格させる。

## 2. なぜ分けるか（検証で分かったこと）

2026-08-27〜28 の PoC（使い捨て 3 サイト、テーマ A/B との同一サイト構築比較、スタイル 3 案、共有パーツ 22 パターン、Figma 往復、エディタ検証）から:

| 分かったこと | 含意 |
|---|---|
| 本テーマの優位は「構造まで GUI/JSON で自由に編集でき、AI が同じ JSON で操作できる」こと。デザインそのものはテーマ A/B に劣る | 自由さは残し、見た目は「実物を並べて選ぶ」で埋まる（3 案・22 パターンで実証） |
| 自由さの代償は一貫性の崩れ。4 層モデル + ゲート（G-T1〜S2, G-T1b, PoC 実機ゲート）で機械的に守れる | 自由と一貫性は両立できるが、**ゲートは製品の一部**として持つ必要がある |
| 静的検査で取れない不具合（Block validation）が繰り返し出た。PoC で実機を開く検証が必須 | 「PoC → 要求 → 設計 → 実装」の証跡側に、エディタ実機検証を固定する |
| Figma は無料枠では配管止まり。中身（デザイン）はテーマ側で作ったほうが早い | デザインの源泉は Figma でなく「パターン群 + スタイル案」 |
| 制御（誰が何をどこまで変えられるか）が未設計。A/B は構造固定・値自由、本テーマは構造自由・値も自由 | GRAPHIX-NEO では **役割別の制御レベル**を最初から設計に入れる |

## 3. それぞれのコンセプト

### 3.1 HELIX-WP-THEME — 「AI と WP 編集の楽しさ」

- **狙う体験**: パターンを差し替え、スタイル案を切り替え、AI に「このセクションを 3 列にして」と頼む。壊れない範囲で何でも試せる。
- **設計方針**
  - 構造は自由（パターン差し替え・ブロック編集・テンプレ変種）。ロックは最小限。
  - 値は 2 段で扱う。**安全域**（プリセット、またはプリセット尺度の内側に収まる任意値）は自由。
    **破壊域**（レイアウトや可読性を壊す値）は**止める**。警告で済ませるのは安全域の生値だけ。
    - 破壊域の例: 余白・フォントサイズが尺度の最大/最小を超える、コントラスト比が AA 未満の色組、
      幅 100% 超・負の余白・vh/vw の過大指定、`!important` の任意 CSS、位置固定 + 高さ過大（画面を覆う）。
    - 実装は theme.json の `custom*` 許可 + 保存時検査（PoC ゲート G-S3 相当をエディタ側にも）+
      レンダー側 CSS clamp（最終防衛線）。境界値は PoC で実物を崩して決める。
  - ゲートは「増やさない」方式（baseline）で、既存の生値は段階的に減らす。破壊域は baseline に関係なく 0 件。
  - 実験的パターンはどんどん入れる（カテゴリ `agent-neo-shared` / `agent-neo-lab` で分ける）。
- **ためる知見**
  - 運用: どのパターンが使われるか、どこで壊れるか、AI が何を苦手とするか（PoC 巡回ログ・エディタ検証の結果）。
  - 開発: save 出力との整合、ゲートの盲点、Figma 等の外部取り込みの実用線。
- **出口**: 使われたパターン・崩れなかった規約だけを GRAPHIX-NEO へ昇格。

### 3.2 GRAPHIX-NEO — 「AIO / LLMO に最適化された正本」

- **狙う成果**: 1 つの Topic Page が 3〜5 本の Context Article を保持し、同一正本から人間 / 検索 / AI 向け表現を生成する（既存コンセプト）。ここに **引用されやすさ**（構造化データ・要約可能な骨格・出典の明示・更新履歴）を設計で入れる。
- **設計方針**
  - 構造は**限定**。WP-THEME で実証済みのパターンだけを採用し、Block Types で差し替え候補を固定。
  - 値は**プリセット強制**（`customFontSize` / `customSpacingSize` / `color.custom` を false）。ゲートは「0 件」方式。
  - 役割別制御: PO/デザイナー = 全層、編集者 = 文言・画像のみ（コンテンツのみ編集 + ロック）、AI = 契約で限定した JSON 書き込み。
  - 記事単位の切替は投稿メタ（テーマ A の 26 キーから必要分だけ）。option による不可視上書きは使わない。
  - AIO/LLMO 要件を**要求 ID で先に確定**し、パターンはその要件を満たす形に絞る（例: 見出し階層の単調性、FAQ の JSON-LD、要約ブロック、出典ブロック、更新日の機械可読化）。
- **入口**: WP-THEME から昇格したパターンとスタイル案、ゲート群、PoC 手順。

## 4. 昇格の規約（WP-THEME → GRAPHIX-NEO）

パターン／スタイル案／ゲートを昇格させる条件:

1. PoC エディタで invalid=0、フロント巡回で PHP 警告 0・JS 例外 0（証跡付き）
2. 値がプリセット参照のみ（G-T2 で 0 件）、スラッグ集合が親と同一（G-T1/G-T1b）
3. 4 層の責務どおり（層 3 が層 1 を定義していない、等）
4. AIO/LLMO 要件のいずれかに寄与する（該当要求 ID を持つ）
5. 運用で「使われた」実績、または PO が実物比較で選んだもの

昇格は PR 単位（WP-THEME の commit を参照する）。GRAPHIX-NEO 側で独自改変した場合は WP-THEME に戻さない（一方向）。
