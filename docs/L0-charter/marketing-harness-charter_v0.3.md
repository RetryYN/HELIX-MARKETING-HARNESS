## §1 一言で

**TAKUMI-CMO のマーケティング頭脳を、HELIX 流「証跡と機械ゲートで品質を守る」思想で、
スクラムをベースとした二重改善ループ（ループスクラム）として回すハーネスにする。**

開発のような一方向の工程（V-model）ではなく、マーケティングの本質である
「仮説→実行→計測→学習」の反復を構造の中心に置く。品質は宣言ではなく、
公開 URL・計測値・審査記録という**証跡**で守る。この点は HELIX と同一思想。

## §2 なぜ作るか（課題）

1. **TAKUMI は「プラグイン」であって「ハーネス」ではない** — スキル・手順書は豊富だが、
   品質保証は審査エージェントのプロンプト頼み。機械ゲート・証跡 DB・ループ駆動機構がない。
2. **マーケ成果物は「完了しました」詐欺が最も起きやすい領域** — 書いた／投稿した／計測した、の
   宣言はコード以上に検証されにくい。証跡の必須化が要る。
3. **マーケは反復が本質** — 開発の V-model 的な「凍結して下ろす」構造は合わない。
   戦略も戦術も計測結果で更新され続ける。**ループそのものを機械で駆動する**構造が必要。

## §3 アーキテクチャ — ループスクラム（二重改善ループ）

### 時間軸 — 3 層構造とサイクルの分離

| 層 | 地平線 | サイクルの単位 |
|---|---|---|
| **ブランド計画** | **1 年**（コンテンツが花開くのに要する期間） | 年次で立て、上位ループの北極星になる |
| **上位ループ（戦略）** | ブランド計画の内側 | **ブランドの成長**を単位に回す（成長段階の節目で見直し） |
| **下位ループ（実行）** | 行動計画の内側 | **媒体単位**に回す（媒体ごとに独立したサイクル・回転数） |

サイクルは暦ではなく対象に従う — 上位はブランドの成長で、下位は媒体の特性で回る。
X は日次回転、ブログは週次回転、といった媒体差を許容し、同期を強制しない。

### 上位ループ（戦略ループ）— ブランド成長サイクルで回す

```
リサーチ → 市場分析 → マーケティング戦略 → 行動計画 ─┐
   ↑                                                    │
   └──────────── 改善（下位ループの実測を還流）←────────┘
```

- スパン: **ブランド成長ベース**（1 年のブランド計画の内側で、成長段階の節目ごとに回転）
- 成果物: 市場分析レポート・戦略ドキュメント・行動計画（＝下位ループへの発注書）
- 改善入力: 下位ループから還流する実測値・学習

### 下位ループ（実行ループ）— 計画スパンで回す

```
媒体戦術 → リサーチ → 企画 → 運用 → 計測 ─┐
   ↑                                        │
   └───────── 改善（次スプリントへ）←───────┘
```

- スパン: **媒体単位**（行動計画が媒体ごとにスプリント長を定める。X=日次〜、ブログ=週次〜など媒体特性に従う）
- 成果物: 各媒体での公開物（記事・SNS 投稿・画像・動画）と計測スナップショット
- 媒体ごとに独立して並走（X / note / YouTube / owned media …）。同期は強制しない

### 二重ループの接続

- **下り**: 上位の「行動計画」が下位スプリントのバックログになる
- **上り**: 下位の「計測」が上位の「リサーチ／改善」の入力になる
- **背骨**: KPI ツリー（ハーネス DB 上）。両ループが読むのも書くのもここだけ。
  ループ間で prose の申し送りをしない — **DB に収束しない実測・学習は存在しない扱い**（HELIX P9 の翻訳）

### ペア構造 — HELIX pair_closure のループ版

一方向工程の design⇔test ペアの代わりに、ループ上の 2 つのペアで「片肺 PASS」を禁じる:

1. **企画 ↔ 品質**（コンテンツを閉じるゲート）
   企画で立てた狙い（訴求・ターゲット・検索意図）に対して、品質審査（critic の PASS）が
   対で揃って初めてコンテンツは公開可能になる。企画なき制作物も、審査なき公開も構造的に不可。
2. **計画 ↔ 計測**（ループを閉じ、上位へ還すゲート）
   行動計画で宣言した KPI 目標に対して、計測スナップショットが対で揃って初めて
   スプリントレビューが成立する。この対が**上位戦略へのボトムアップフィードバック**の単位になる —
   計画なき計測値はノイズ、計測なき計画は願望として、どちらも単独では上位ループへ還流しない。

### データ基盤 — 3 つの置き場所

| 置き場所 | 役割 | 保持するもの |
|---|---|---|
| **WordPress** | コンテンツ資産 DB（運用資産の形成先） | テキスト・画像・動画など**重いコンテンツ実体はすべてここ**（メディアライブラリ含む）。公開／下書きの別を問わず、制作物はここに蓄積され再利用可能な資産になる |
| **Notion** | 企画・計画レイヤ | コンテンツのネタ帳、行動計画、スプリントバックログ、編集カレンダー |
| **ハーネス DB**（ローカル SQLite） | 背骨 | **数値・状態管理に限定**: KPI ツリー・施策状態・計測時系列・ペア成立判定・証跡（公開 URL / 審査記録 / WP メディアへの参照）。バイナリは持たず、コンテンツ実体は WordPress 側の URL/ID で参照する |

- **編集基盤（制作の作業場）はローカルの git 管理ワークスペース** — ハーネス本体とは別リポジトリの
  「ブランドワークスペース」に、台本・原稿（drafts/）、制作ソース（assets-src/: SVG・Remotion・bpy 等）を置く。
  制作源泉はコードなので git の差分・履歴がそのまま編集履歴になり、審査 PASS した版を commit hash で証跡化できる。
  レンダリング済み中間物は git 管理外とし、完成品を WordPress へ納めた時点でローカルを掃除する
- フローは **Notion（ネタ・計画）→ ワークスペースで制作（git）→ WordPress（資産化・公開）→ 計測 → ハーネス DB（証跡・還流）**
- WordPress は単なる公開先ではなく**運用資産の形成先**。過去コンテンツの構造・実績が次の企画の入力になる
- ペア成立の判定（企画↔品質、計画↔計測）はハーネス DB が持つ。Notion / WordPress は判定正本にしない

### スクラム要素の対応

| スクラム | 本ハーネス |
|---|---|
| プロダクトバックログ | 上位ループの行動計画 |
| スプリント | 下位ループの 1 回転（計画スパン） |
| スプリントレビュー | 計測ゲート（証跡が揃って初めてレビュー成立） |
| レトロスペクティブ | 改善ステップ（学習の DB 収束＋次スプリント計画へ反映） |
| インクリメント | 公開された成果物＋計測スナップショット |

## §4 自律境界（人/AI の分担）

**原則: 企画以降はヒューマンアウトオブループ**（HELIX 思想の継承）。
人が関与するのは企画（本チャーター＋事業前提）の確定までであり、以降の戦略・計画・実行・計測・改善は
すべて AI がガードレールの内側で自走する。品質は人の承認ではなく、ペアゲートと証跡が守る。

| 工程 | 担当 |
|---|---|
| 企画: 本チャーター・事業前提・ブランド線・倫理線・予算制約（ゼロ広告費）の確定 | **人**（最後の直接関与） |
| ブランド計画・市場分析・戦略・行動計画（上位ループ全工程） | **AI が自走**（人の承認なし） |
| 下位ループ全工程（媒体戦術→リサーチ→企画→運用→計測→改善） | **AI が自走** |
| 外部公開（投稿・公開）という高影響 action | 経過措置としてスマホ連携の束縛承認 → 安定稼働の証跡が揃い次第オートモードへ移行し、完全アウトオブループ（§10 ④） |

## §5 柱（P0–P5 案）

- **P0 ゼロ広告費ゲート** — 有料指標・広告経路の機械遮断（TAKUMI 継承）。fail-close
- **P1 証跡必須の完了判定（ペア成立）** — 「企画↔品質」「計画↔計測」の対が DB 上で揃うまで done にならない。片肺 PASS 禁止
- **P2 二重ループ駆動エンジン** — 上位=期間スパン、下位=計画スパンの回転を機械が駆動。
  スプリントの開始・レビュー・還流を宣言でなく状態機械で進める
- **P3 KPI ツリー = 単一の背骨** — 両ループの読み書きは DB 上の KPI ツリーに収束。学習のサイロ禁止。
  将来構想として**オーガニック版 MMM**: 媒体別サイクルの実測を横断集計し、各媒体の露出がブランド KPI へ
  どれだけ寄与したかを分解するモデル（媒体単位の計測とマーケティング全体の計測を紐づける層）。
  KPI ツリーのスキーマは初期からこの横断集計を見越して設計する
- **P4 エージェント分業と相互監査** — strategist / writer / critic / verifier を分離。作った本人に審査させない
- **P5 倫理線** — 心理学は不安の解消に使い増幅に使わない。恐怖訴求・偽の希少性は機械側でも却下

## §6 継承と新規

### TAKUMI から継承

継承方針: **そのまま移植ではなく、スキル・ワークフロー・タスク定義を素材として取り出し、
本ハーネスのループスクラム構造に合わせて HELIX 風にカスタマイズする**。

| 資産 | 扱い |
|---|---|
| skills/（約40本: seo-jp, copywriting, stp-jp, kpi-design-jp …） | 素材として取り込み、二重ループの各ステップへ再配置・改修 |
| procedures/（takumi-* ワークフロー・タスク） | ループ各ステップの駆動定義に再編（最重要の取り込み対象） |
| agents/（10本: cmo-strategist, design-critic, outcome-verifier …） | 役割は参考に、ペアゲート連携前提で再設計 |
| commands/ | 継承しない（§10 ②: コマンド体系は持たない）。内部のワークフロー記述のみ素材として参照 |
| ∞ループ思想 | 本チャーターの二重ループとして正式アーキテクチャ化 |

### 制作スタック — コード×ブラウザレンダリング主軸

制作物は「生成 AI に描かせる」より「**コードで作ってブラウザでレンダリングする**」を主軸にする
（決定的・再現可能・証跡が残る。HELIX 思想と整合）。ブラウザは SNS 突破・証跡スクショ・レンダリングの三役。

| 制作物 | 手段 |
|---|---|
| 図解・OGP・バナー・サムネ | HTML/SVG/CSS をコード生成 → ブラウザでスクショ画像化 |
| スライド | HTML スライドをコード生成 → PDF/画像化（既存資産 slide-monster を素材候補に） |
| 診断ツール・シミュレータ | HTML/JS で作成し WordPress に埋め込み（リード獲得コンテンツ） |
| 3D | three.js（軽量・ブラウザ実行）＋ **Blender ヘッドレス**（bpy/Python スクリプトから高品質レンダリング。ハーネスの Python と直結） |
| 音声 | **VOICEVOX**（ローカル TTS、無料・商用可）。動画ナレーション用。localhost API なのでゼロ API 費の原則に反しない |
| 動画 | Remotion + ffmpeg で「コードから動画」。台本→VOICEVOX 音声→図解/Blender 素材→ffmpeg 合成の解説動画パイプライン。生成 AI 動画は下記ブラウザ経由 |
| 生成 AI 画像・動画 | **保有アカウント（ChatGPT / Gemini / Grok 等）の Web UI をブラウザ自動化で操作して生成**。API 課金はしない（SNS と同じ「ブラウザで突破」の一貫戦略）。生成物のダウンロードと生成時プロンプトを証跡として DB へ |
| ストック素材（写真・映像クリップ・BGM） | **Canva をブラウザ自動化で素材調達庫として使う**（保有アカウント）。デザイン制作は Canva 上では行わない（コード×デザイントークンの主軸を崩さない）。取得素材と利用先は DB で紐づけ管理 |
| 生成 AI 動画（例外） | **Seedance API のみ有償利用を許可**（ゼロ API 費原則の明示的例外。低コストで、実写風・モーション系はブラウザ経由では回転数が出ないため）。利用コストと生成プロンプトを証跡として DB に記録し、支出を可視化する |

コーディング量の多い制作（診断ツール等）は Codex プラグイン（コーディング支援）を併用できる。画像生成能力は持たない。

### デザインシステム — Claude Design 連携（必須）

ブランドのデザインシステム（配色・タイポグラフィ・コンポーネント）を **claude.ai/design のプロジェクトに
正本として置き、DesignSync でローカルと同期**する。全制作物（OGP・図解・スライド・LP・診断ツール・
WP 子テーマ）は同じデザイントークンから生成し、ブランド一貫性を注意でなく仕組みで守る。
ブランド線（§4 で人が確定する領域）の機械的実体がこのデザインシステムになる。

### WordPress 開発方針 — テーマ解析 × 子テーマ拡張

フルスクラッチのテーマ開発はしない。**既存テーマを解析して使い、子テーマ＋小さなカスタムプラグインで
拡張する**のを基本とする（親テーマの SEO・レスポンシブ・a11y の蓄積を活かし、更新にも壊されない）。

- 子テーマ: デザイントークン（Claude Design 由来）の反映、テンプレート断片の上書き
- カスタムプラグイン: 診断ツール埋め込み・ショートコード・REST 拡張
- Gutenberg カスタムブロック: 記事内で再利用する図解・CTA・診断パーツ
- カスタム投稿タイプ: コンテンツ資産の構造化（事例・用語集など）
- テーマ解析結果（構造・フック・スタイル体系）は攻略地図として DB に残す

### ダッシュボード — HTML 主・スプレッドシート従

分析ダッシュボードは **SQLite から Python で HTML を自動生成**するのを主とする（完全自動・証跡化可能）。
Notion HQ には数値サマリの書き戻しと HTML ダッシュボードの埋め込みのみ（Notion のチャートは使わない）。
従として、人が手でピボット探索したいとき用に**計測時系列を xlsx でエクスポート**できるようにし、
ブラウザ経由でスプレッドシートへ投入する（F3 で実装）。

### 計測データの取り込み — ブラウザエクスポート → 解体 → SQLite

GA4・Google タグマネージャ・Search Console などの計測系は **API 連携しない**（設定・認証・クォータが面倒で
保守負担になる）。代わりに**ブラウザ自動化で管理画面から Excel/CSV をエクスポートし、パースして SQLite の
計測時系列へ投入する**。取得スクショとエクスポートファイルのハッシュを証跡として残す。
SNS のインプレッション等も同様にブラウザ経由で取得 — 計測もすべて「ブラウザで突破」に統一。

### SNS 運用 — ブラウザで突破

SNS（X / note / Instagram / YouTube …）の投稿・計測は **API 契約ではなくブラウザ自動化で行う**
（TAKUMI の「実ブラウザで計測し、証跡を残す」路線の継承）。
公式 API の課金・審査・レート制約に依存しない。攻略したサイト構造は地図として DB に残し、次回実行を速くする。
スクリーンショット・公開 URL をブラウザ経由で取得し、そのまま証跡にする。

### 新規（HELIX 流）

1. 証跡ゲート（P1）とハーネス DB（KPI ツリー・施策・証跡・実測）
2. 二重ループの状態機械（P2）— どのスプリントの、どのステップに、何が滞留しているかを機械が把握
3. HELIX ローダ互換（`@...` import で HELIX 本体から読める構成）
4. 外部基盤コネクタ — WordPress（REST API + WP-CLI。内部構築含む）と Notion（MCP）への読み書き。証跡・判定はハーネス DB 側に持つ

### 非スコープ

- 広告運用（変数として 0 に固定）
- 人間チーム運用（velocity / ceremony。スクラムは AI の反復機構としてのみ採用）
- HELIX 本体（開発ハーネス）の変更

## §10 確定事項

- **WordPress 接続方式（⑥ 確定 2026-07-30）**: コンテンツ運用は **REST API 直（Application Passwords）**。
  MCP は採用しない（決定的レスポンスの証跡保存・無人自走・fail-close の観点で REST 直が優位）。
  **WP の内部構築（サイト初期設定・テーマ・プラグイン・構造）もスコープに含め、WP-CLI で行う**
  （ローカル Docker WP で構築→検証→本番反映の流れを想定）。対象サイトは別途指定。
- **Notion 構造（⑦ 確定 2026-07-30）**: 専用のフリー Notion ワークスペースを使用。
  構造設計は AI が実施済み — HQ ページ配下に 📋 行動計画 / 💡 ネタ帳（編集カレンダー・制作ボード付き）/
  🏃 スプリントバックログ（スプリントボード付き）の 3 DB をリレーション接続で構築（2026-07-30）。
- **SNS 接続方式（確定 2026-07-30）**: API ではなく**ブラウザ自動化で突破**。サイト構造の攻略地図を DB に蓄積。
- **TAKUMI 継承方針（確定 2026-07-30）**: そのまま移植ではなく、スキル・ワークフロー・タスクを素材として
  取り出し、ループスクラム構造へ HELIX 風にカスタマイズして再配置する。
- **コマンド体系（② 確定 2026-07-30）**: **専用コマンドは持たない**。ハーネスの状態機械が次アクションを
  把握しているため、人が工程をコマンドで呼び出す構造は不要。入口は自然言語＋定時実行（cron/heartbeat）。
  TAKUMI のコマンド群・「匠」の呼称・文言は一切継承しない（機能素材のみ取り込む）。
- **公開承認（④ 確定 2026-07-30）**: 公開直前に**スマホ連携（プッシュ通知）で束縛承認**。
  安定稼働の実績（証跡ベース）が積み上がったら**オートモードへ段階移行**し、人の承認なしで公開まで自走。
- **ライセンス（⑤ 確定 2026-07-30）**: 現段階では設定しない。公開配布を決める時点で再検討。
- **ハーネス DB（確定 2026-07-30）**: **SQLite** を採用し、**数値・状態管理に限定**（KPI ツリー・施策状態・計測時系列・ペア成立判定・証跡参照）。
  画像・動画など重いコンテンツ実体は WordPress（メディアライブラリ）に保管し、SQLite からは URL/ID 参照のみ。
  Notion は人が触る計画・ネタ・カレンダーの UI に限定し、同期は低頻度（スプリント開始時の読取り／レビュー成立時の書戻し）。
  高頻度の読み書きはすべて SQLite 側に寄せる。
- **時間軸・サイクル（① 確定 2026-07-30）**: ブランド計画は **1 年**で立てる（コンテンツが花開く期間）。
  サイクルは**媒体単位（下位）とブランドの成長（上位）で分離**し、暦ではなく対象に従って回す。
  将来的に MMM 的な全体計測（オーガニック版）と紐づける — P3 に記載。
- **実装言語（③ 確定 2026-07-30）**: ハーネス本体（状態機械・ゲート判定・KPI ツリー DB・意味判断）は **Python**。
  データと意味を扱う中核であり、HELIX 本体の「Python = semantic core」方針とも一致する。
  WordPress 側の構築・カスタマイズでは **PHP / HTML / CSS / JavaScript** を扱う（テーマ・プラグイン・LP 等）。
