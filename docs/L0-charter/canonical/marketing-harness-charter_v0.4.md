## §1 一言で

**TAKUMI-CMO のマーケティング頭脳を、HELIX 流「証跡と機械ゲートで品質を守る」思想で、
上流戦略 OS と下流戦術 OS を二重改善ループとして接続し、下流は pull・WIP 制限・blocked 管理・flow 計測を持つ Kanban を常時運転の主軸、Scrum は replenishment・review・retrospective の cadence として使うハーネスにする。**

HELIX-HARNESS は本製品へ組み込む runtime dependency ではない。本リポジトリの要求・設計・実装・検証を進める開発方式として使用し、製品内部の運転モデルとは分離する。

製品 runtime は開発工程の V-model を模倣せず、マーケティングの本質である
「仮説→実行→計測→学習」の反復を構造の中心に置く。品質は宣言ではなく、
公開 URL・計測値・審査記録という**証跡**で守る。この点は HELIX と同一思想。

## §2 なぜ作るか（課題）

1. **TAKUMI は「プラグイン」であって「ハーネス」ではない** — スキル・手順書は豊富だが、
   品質保証は審査エージェントのプロンプト頼み。機械ゲート・証跡 DB・ループ駆動機構がない。
2. **マーケ成果物は「完了しました」詐欺が最も起きやすい領域** — 書いた／投稿した／計測した、の
   宣言はコード以上に検証されにくい。証跡の必須化が要る。
3. **マーケは反復が本質** — 開発の V-model 的な「凍結して下ろす」構造は合わない。
   戦略も戦術も計測結果で更新され続ける。**ループそのものを機械で駆動する**構造が必要。

## §3 アーキテクチャ — 戦略 OS ↔ 戦術 OS（二重改善ループ）

### 3.0 開発方式と製品運転モデルの分離

- **外側（開発）**: HELIX の L1〜L12 V-model、Forward/Reverse、要件↔検証ペア、証跡ゲートで本製品を開発する。
- **内側（製品 runtime）**: 下流戦術 OS は Kanban の pull system として連続運転する。スプリントは作業を一括投入する箱ではなく、補充・レビュー・振り返りを行う時間境界である。
- 上流戦略 OS は市場・顧客・価値仮説・戦略選択・媒体役割・KPI を版付き brief として下流へ渡す。下流戦術 OS は実行・計測の事実と解釈を分離した TLP を上流へ返す。どちらも相手の正本を直接更新しない。
- 上流の revision により実媒体は追加・一時停止・廃止・差替えできる。戦略上の `media_role`、実媒体への `media_binding`、接続経路を分離し、媒体名を kernel・固定フォルダ構造・状態機械へ焼き付けない。
- `business_profile` は隔離境界、その配下の `bounded_domain` は業務コンテキスト、`media_binding` は domain 内で版管理される実行資源とする。1 profile は複数 domain を持てるが、domain 間・profile 間の暗黙共有は禁止する。

### 時間軸 — 3 層構造とサイクルの分離

| 層 | 地平線 | サイクルの単位 |
|---|---|---|
| **ブランド計画** | **1 年**（コンテンツが花開くのに要する期間） | 年次で立て、上位ループの北極星になる |
| **上位ループ（戦略）** | ブランド計画の内側 | **ブランドの成長**を単位に回す（成長段階の節目で見直し） |
| **下位ループ（実行）** | 行動計画の内側 | **媒体単位**に回す（媒体ごとに独立したサイクル・回転数） |

サイクルは暦ではなく対象に従う — 上位はブランドの成長で、下位は媒体の特性で回る。
X は日次回転、ブログは週次回転、といった媒体差を許容し、同期を強制しない。

### 上位ループ（戦略ループ）— ブランド成長サイクルで回す

```text
リサーチ → 市場分析 → マーケティング戦略 → 行動計画 ─┐
   ↑                                                    │
   └──────────── 改善（下位ループの実測を還流）←────────┘
```

- スパン: **ブランド成長ベース**（1 年のブランド計画の内側で、成長段階の節目ごとに回転）
- 成果物: 各工程の出力を**機械可読の意味モデル**へ固定する（prose レポートではない） —
  リサーチ = market_observation（事実と AI 解釈の混在禁止）、市場分析 = market_model・segment_context・
  problem_model、戦略 = value_hypothesis・category_definition・positioning_hypothesis・causal_assumption・
  strategic_choice（棄却案と棄却理由も保持）、行動計画 = strategic_brief（下位ループへの発注契約。
  下位ループは有効な brief なしに開始できない）、改善 = strategy_revision（根拠・反証・信頼度・対象版つき）
- 改善入力: 下位ループが完了時に提出する tactical_learning_packet（観測・解釈・因果・反証可能仮説・
  推奨判断を分離）。**下位ループは上流戦略正本を直接更新できない** — 戦略変更の決定は上位ループが
  複数の観測・反証・時間差を評価して行い、正本は supersedes による append-only 版管理とする
- 学習対象の分離: 上位ループは「何を市場と捉え、誰のどの状況に、どの価値を定義し、どの選択基準を
  形成するか」を学習する。下位ループは「確定した戦略仮説の範囲内で、どの媒体・表現・運用が有効か」を
  学習する。両者を一つの PDCA へ統合しない。**上位ループの一周は、市場の捉え方・セグメント・問題定義・
  未充足価値・カテゴリー・比較軸・価値提案・ポジショニング・戦略仮説・戦略判断のいずれかが
  revision を経て更新されたときにのみ成立する**（KPI を受けた行動計画の微修正だけでは一周と数えない —
  上流ループを月次 KPI レビューへ縮退させない）
- セグメントの定義原則: 時間・空間・状況・制約・進行状態・問題の顕在度・既存の代替行動・意思決定条件・
  利用可能な資源・変化のトリガーを中心とする。**年齢・性別・職業・趣味中心の架空人物ペルソナを
  正本として導入しない**（人口統計属性は補助変数のみ。人口統計だけのセグメントは機械ゲートで拒否）
- コンテンツの位置づけ: コンテンツは投稿物・集客物ではなく、**市場の問題認識・カテゴリー・比較軸・
  選択基準・価値認識を定義・変化させるマーケティング資産**である。主要コンテンツ企画は
  「定義する問題・変化させる認識・提示する比較軸・定義する価値・対象となる戦略仮説」を必ず宣言する

### 下位ループ（実行ループ）— 計画スパンで回す

```text
媒体戦術 → リサーチ → 企画 → 運用 → 計測 ─┐
   ↑                                        │
   └───────── 改善（次スプリントへ）←───────┘
```

- スパン: **媒体単位**（行動計画が媒体ごとにスプリント長を定める。X=日次〜、ブログ=週次〜など媒体特性に従う）
- 成果物: 各媒体での公開物（記事・SNS 投稿・画像・動画）と計測スナップショット
- 媒体ごとに独立して並走（X / note / YouTube / owned media / Discord コミュニティ …）。同期は強制しない

### 二重ループの接続

- **下り**: 上位の行動計画が発行する **strategic_brief**（digest 付き契約）が下位スプリントのバックログになる
- **上り**: 下位の計測・学習は **tactical_learning_packet** として上位の「リサーチ／改善」へ還流する
- **観測背骨**: KPI ツリー（ハーネス DB 上）。**観測結果・事業成果を接続する背骨であり、戦略正本ではない** —
  「なぜその結果が発生したと考えるか」は市場・価値・戦略の意味モデルが保持し、数値が変化しただけで
  戦略を自動変更しない（単一 KPI 変動での自動 revision 禁止）。
  ループ間で prose の申し送りをしない — **DB に収束しない実測・学習は存在しない扱い**（HELIX P9 の翻訳）

### ペア構造 — HELIX pair_closure のループ版

一方向工程の design⇔test ペアの代わりに、ループ上の 2 つのペアで「片肺 PASS」を禁じる:

1. **企画 ↔ 品質**（コンテンツを閉じるゲート）
   企画で立てた狙い（訴求・ターゲット・検索意図）に対して、品質審査（critic の PASS）が
   対で揃って初めてコンテンツは公開可能になる。企画なき制作物も、審査なき公開も構造的に不可。
2. **計画 ↔ 計測**（ループを閉じ、上位へ還すゲート）
   行動計画で宣言した KPI 目標に対して、計測スナップショットが対で揃って初めて
   スプリントレビューが成立する。この対が**上位戦略へのボトムアップフィードバック**の単位になる —
   計画なき計測値はノイズ、計測なき計画は願望として、どちらも単独では上位ループへ還流しない。

### データ基盤 — 3 つの置き場所

| 置き場所 | 役割 | 保持するもの |
|---|---|---|
| **WordPress** | コンテンツ資産 DB（運用資産の形成先） | テキスト・画像・動画など**重いコンテンツ実体はすべてここ**（メディアライブラリ含む）。公開／下書きの別を問わず、制作物はここに蓄積され再利用可能な資産になる |
| **Notion** | 企画・計画レイヤ | コンテンツのネタ帳、行動計画、スプリントバックログ、編集カレンダー |
| **ハーネス DB**（ローカル SQLite） | 背骨 | **数値・状態管理に限定**: KPI ツリー・施策状態・計測時系列・ペア成立判定・証跡（公開 URL / 審査記録 / WP メディアへの参照）。バイナリは持たず、コンテンツ実体は WordPress 側の URL/ID で参照する |

- **収益レイヤ（確定 2026-07-30）**: **Stripe** で自社販売の決済（決済リンク/Checkout を WP に埋め込み。
  手数料は取引ベースで固定費ゼロ。接続は公式 MCP 優先）。**note のコンテンツ販売**（有料記事・マガジン）は
  ブラウザ突破で運用。売上・販売数は KPI ツリーの収益系指標として SQLite へ還流し、
  露出→転換→関係→収益の四層で媒体寄与を追う。
  **ただし金銭を動かす操作（価格変更・返金・決済設定変更）はオートモード移行後も人間の束縛承認に残す**（escalation 境界）。
- **マイクロコンバージョン資料（確定 2026-07-30）**: ホワイトペーパー・チェックリスト・テンプレート・
  事例集などのリードマグネットを、スライド生成パイプライン（HTML→PDF・デザイントークン適用）で量産。
  記事内 CTA・診断ツール結果画面から HubSpot フォームでゲートして DL 提供。
  KPI ツリーに**マイクロ CV 層**（資料 DL 率・フォーム完了率・診断完走率・メルマガ/LINE 登録）を正式に持たせ、
  コンテンツ単位で露出→読了→マイクロ CV→リードの歩留まりを SQLite で追う。
- **プッシュ型配信（確定 2026-07-30）**: **メルマガ = HubSpot 無料枠**（月 2,000 通。リードレイヤと同居、
  原稿は WP 記事のリパーパス、MCP 優先。超過時に配信専業の無料枠か有料化を判断）。
  **LINE = LINE 公式アカウント フリープラン**（月 200 通。管理画面をブラウザ突破。一斉配信ではなく
  SQLite/HubSpot のデータで見込み度を判定した**セグメント配信専用の高密度チャネル**として設計）。
  KPI は関係系（開封・クリック・ブロック率）として SQLite へ。
- **アフィリエイト（確定 2026-07-30）**: ASP（A8.net・もしも・Amazon アソシエイト・楽天等）を
  **ブラウザ突破**で運用 — 案件検索・提携申請・リンク発行・WP 記事への埋め込み・成果レポート取得（→SQLite 収益系）。
  **広告表記（PR 表記）の自動挿入を品質ゲートに組み込み、ステマ規制を機械側で遵守**（P5 倫理線の適用）。
- **App 系（確定 2026-07-30）**: **主 = PWA**（診断ツール等を manifest+SW でアプリ化。費用ゼロ・審査なし・
  完全コード駆動）。**従 = Google Play**（登録 $25 買い切り。PWA を TWA パッケージで出しストア面の露出を獲得）。
  **iOS App Store は保留**（年 $99 の固定費と審査リスク。成果が出てから再検討）。
- **音声メディア（確定 2026-07-30）**: 三段構え。**主 = ポッドキャスト**（WP に RSS を生やし
  Spotify/Apple/Amazon Music へ配信。台本→VOICEVOX→mp3→WP メディアで完全コード駆動・審査なし）。
  **従 = stand.fm**（審査なし・ブラウザ突破）。**オプション = Voicy**（審査制・肉声文化のため
  審査通過時のみ参入検討）。動画パイプラインの音声を流用し、動画 1 本から音声版を副産物として得る。
- **Amazon KDP 出版（確定 2026-07-30）**: 電子書籍出版を媒体兼収益源として追加。WP 資産記事をテーマ別に
  再編 → pandoc で EPUB 生成（コード駆動）→ KDP へ**ブラウザ突破**でアップ・売上取得（KDP は API なし）。
  Amazon という独立した発見面への露出＋ロイヤリティ収益。価格操作は上記 escalation 境界に従う。
- **HubSpot（無料枠）= リード・顧客レイヤ** — 診断ツール・フォーム・LP のリード受け皿と CRM。
  接続は公式 MCP 優先＋ブラウザ補完。ナーチャリング等の自動化は HubSpot の有料機能を買わず
  **ハーネス側のループが SQLite の判定に基づいて駆動**する。リード数・転換は KPI ツリーの転換系指標として SQLite へ還流
- **編集基盤（制作の作業場）はローカルの git 管理ワークスペース** — ハーネス本体とは別リポジトリの
  「ブランドワークスペース」に、台本・原稿（drafts/）、制作ソース（assets-src/: SVG・Remotion・bpy 等）を置く。
  制作源泉はコードなので git の差分・履歴がそのまま編集履歴になり、審査 PASS した版を commit hash で証跡化できる。
  レンダリング済み中間物は git 管理外とし、完成品を WordPress へ納めた時点でローカルを掃除する
- フローは **Notion（ネタ・計画）→ ワークスペースで制作（git）→ WordPress（資産化・公開）→ 計測 → ハーネス DB（証跡・還流）**
- WordPress は単なる公開先ではなく**運用資産の形成先**。過去コンテンツの構造・実績が次の企画の入力になる
- ペア成立の判定（企画↔品質、計画↔計測）はハーネス DB が持つ。Notion / WordPress は判定正本にしない

### Scrum cadence の対応

| スクラム | 本ハーネス |
|---|---|
| プロダクトバックログ | 上位ループの行動計画 |
| スプリント | Kanban を停止しない補充・レビューの時間境界（WIP を一括投入する箱ではない） |
| スプリントレビュー | 計測ゲート（証跡が揃って初めてレビュー成立） |
| レトロスペクティブ | 改善ステップ（flow 指標と学習の DB 収束＋次の replenishment 方針へ反映） |
| インクリメント | 公開された成果物＋計測スナップショット |

### 実行モデル — 外殻はループ、内部はタスク×ワークフロー

| 層 | 役割 | 性質 |
|---|---|---|
| **ループ（外殻）** | 回転の駆動 — スプリント開始・ペアゲート・還流を状態機械が進める | 事業・媒体に依存しない不変の骨格 |
| **タスク** | ループの各ステップが発行する作業単位。状態・担当エージェント・証跡を SQLite で管理 | ループが生成し、完了はゲートが判定 |
| **ワークフロー** | **タスク 1 件に 1 本**割り当てられる実行手順の定義（TAKUMI の skills/procedures をカスタマイズした素材が入る場所） | 差し替え・追加が自由。媒体追加＝ワークフロー追加 |
| **検証マイクロループ** | 各タスク内部の**実行エージェント×検証エージェントの反復** — 作る→検証→差し戻し→…→PASS で初めてタスク完了。リトライ上限で上位へエスカレーション | P4（自己審査禁止）のタスク粒度での機械化。HELIX P2 のループ単位実行の翻訳 |

ループは三重構造になる: **上位ループ（戦略・ブランド成長）⊃ 下位ループ（媒体・スプリント）⊃
検証マイクロループ（タスク単位）**。外殻（ループ）に触らずワークフローを足すだけで能力が増える構造にする —
スライス駆動（§7）・型×動的充填（下記）と同型の拡張原理。

### 横断原則 — 型×動的充填（ハーネスは事業非依存のエンジン）

本ハーネスは特定事業のマーケティング実装ではなく、**どの事業を差し込んでも回る「型（スキーマ）＋
動的充填」のエンジン**として設計する。具体値をハードコードせず、充填経路を型ごとに定める:

| 型 | 充填経路 |
|---|---|
| 事業前提（ブランド・顧客・商品・NG 領域）・受入基準 | **ヒアリングエンジン** — 不足スロットを検出し、構造化ヒアリングで人に問診して充填（人が書類を書くのではなく、エンジンが聞きに来る） |
| KPI ツリーの初期形・業種/媒体の標準指標・運用詳細（ホスティング仕様等） | **リサーチエンジン** — Web 検索・外部照合で動的取得し AI が起草（HELIX P8 の翻訳） |
| 安全側の数値（支出上限・レート・オート移行基準） | **設定管理** — config として SQLite に保持し、変更履歴を証跡化 |

事業前提の確定（§4 で人が担う領域）は、このヒアリングエンジンへの回答という形で行われる。

## §4 自律境界（人/AI の分担）

**原則: 企画以降はヒューマンアウトオブループ**（HELIX 思想の継承）。
人が関与するのは企画（本チャーター＋事業前提）の確定までであり、以降の戦略・計画・実行・計測・改善は
すべて AI がガードレールの内側で自走する。品質は人の承認ではなく、ペアゲートと証跡が守る。

| 工程 | 担当 |
|---|---|
| 企画: 本チャーター・事業前提・ブランド線・倫理線・予算制約（ゼロ広告費）の確定 | **人**（最後の直接関与） |
| ブランド計画・市場分析・戦略・行動計画（上位ループ全工程） | **AI が自走**（人の承認なし） |
| 下位ループ全工程（媒体戦術→リサーチ→企画→運用→計測→改善） | **AI が自走** |
| 外部公開（投稿・公開）という高影響 action | 経過措置としてスマホ連携の束縛承認 → 安定稼働の証跡が揃い次第オートモードへ移行し、完全アウトオブループ（§10 ④） |

## §5 柱（P0–P5 案）

- **P0 ゼロ広告費ゲート** — 有料指標・広告経路の機械遮断（TAKUMI 継承）。fail-close
- **P1 証跡必須の完了判定（ペア成立）** — 「企画↔品質」「計画↔計測」の対が DB 上で揃うまで done にならない。片肺 PASS 禁止
- **P2 二重ループ駆動エンジン** — 上位=期間スパン、下位=計画スパンの回転を機械が駆動。
  スプリントの開始・レビュー・還流を宣言でなく状態機械で進める
- **P3 KPI ツリー = 単一の背骨** — 両ループの読み書きは DB 上の KPI ツリーに収束。学習のサイロ禁止。
  将来構想として**オーガニック版 MMM**: 媒体別サイクルの実測を横断集計し、各媒体の露出がブランド KPI へ
  どれだけ寄与したかを分解するモデル（媒体単位の計測とマーケティング全体の計測を紐づける層）。
  KPI ツリーのスキーマは初期からこの横断集計を見越して設計する
- **P4 エージェント分業と相互監査** — strategist / writer / critic / verifier を分離。作った本人に審査させない
- **P5 倫理線** — 心理学は不安の解消に使い増幅に使わない。恐怖訴求・偽の希少性は機械側でも却下

## §6 継承と新規

### TAKUMI から継承

継承方針: **そのまま移植ではなく、スキル・ワークフロー・タスク定義を素材として取り出し、
本ハーネスのループスクラム構造に合わせて HELIX 風にカスタマイズする**。

| 資産 | 扱い |
|---|---|
| skills/（約40本: seo-jp, copywriting, stp-jp, kpi-design-jp …） | 素材として取り込み、二重ループの各ステップへ再配置・改修 |
| procedures/（takumi-* ワークフロー・タスク） | ループ各ステップの駆動定義に再編（最重要の取り込み対象） |
| agents/（10本: cmo-strategist, design-critic, outcome-verifier …） | 役割は参考に、ペアゲート連携前提で再設計 |
| commands/ | 継承しない（§10 ②: コマンド体系は持たない）。内部のワークフロー記述のみ素材として参照 |
| ∞ループ思想 | 本チャーターの二重ループとして正式アーキテクチャ化 |

### 制作スタック — コード×ブラウザレンダリング主軸

制作物は「生成 AI に描かせる」より「**コードで作ってブラウザでレンダリングする**」を主軸にする
（決定的・再現可能・証跡が残る。HELIX 思想と整合）。ブラウザは SNS 突破・証跡スクショ・レンダリングの三役。

| 制作物 | 手段 |
|---|---|
| 図解・OGP・バナー・サムネ | HTML/SVG/CSS をコード生成 → ブラウザでスクショ画像化 |
| スライド | HTML スライドをコード生成 → PDF/画像化（既存資産 slide-monster を素材候補に） |
| 診断ツール・シミュレータ | HTML/JS で作成し WordPress に埋め込み（リード獲得コンテンツ） |
| 3D | three.js（軽量・ブラウザ実行）＋ **Blender ヘッドレス**（bpy/Python スクリプトから高品質レンダリング。ハーネスの Python と直結） |
| 音声 | **VOICEVOX**（ローカル TTS、無料・商用可）。動画ナレーション用。localhost API なのでゼロ API 費の原則に反しない |
| 動画 | Remotion + ffmpeg で「コードから動画」。台本→VOICEVOX 音声→図解/Blender 素材→ffmpeg 合成の解説動画パイプライン。生成 AI 動画は下記ブラウザ経由 |
| 生成 AI 画像・動画 | **保有アカウント（ChatGPT / Gemini / Grok 等）の Web UI をブラウザ自動化で操作して生成**。API 課金はしない（SNS と同じ「ブラウザで突破」の一貫戦略）。生成物のダウンロードと生成時プロンプトを証跡として DB へ |
| ストック素材（写真・映像クリップ・BGM） | **Canva をブラウザ自動化で素材調達庫として使う**（保有アカウント）。デザイン制作は Canva 上では行わない（コード×デザイントークンの主軸を崩さない）。取得素材と利用先は DB で紐づけ管理 |
| 生成 AI 動画（例外） | **Seedance API のみ有償利用を許可**（ゼロ API 費原則の明示的例外。低コストで、実写風・モーション系はブラウザ経由では回転数が出ないため）。利用コストと生成プロンプトを証跡として DB に記録し、支出を可視化する |

コーディング量の多い制作（診断ツール等）は Codex プラグイン（コーディング支援）を併用できる。画像生成能力は持たない。

### 外部接続の一般原則 — MCP → ブラウザ → 有償 API

外部サービスへの接続は次の優先順位で選ぶ:

1. **公式 MCP コネクタ**（Canva・Notion 等）— OAuth 認証・課金なし・構造化データ。最優先
2. **ブラウザ自動化**（SNS・GA4・Search Console・生成 AI Web UI）— MCP がない、または機能不足のとき。
   MCP 採用サービスのフォールバックとしても機能する
3. **有償 API** — 明示的例外のみ（現状 Seedance のみ。WordPress REST は自前サイトのため無償扱い）

MCP はアカウント認証ベースでありゼロ API 費原則に反しない。いずれの経路でも証跡（取得物・操作記録）は DB へ。

### デザインシステム — Claude Design 連携（必須）

ブランドのデザインシステム（配色・タイポグラフィ・コンポーネント）を **claude.ai/design のプロジェクトに
正本として置き、DesignSync でローカルと同期**する。全制作物（OGP・図解・スライド・LP・診断ツール・
WP 子テーマ）は同じデザイントークンから生成し、ブランド一貫性を注意でなく仕組みで守る。
ブランド線（§4 で人が確定する領域）の機械的実体がこのデザインシステムになる。

### WordPress 開発方針 — テーマ解析 × 子テーマ拡張

フルスクラッチのテーマ開発はしない。**既存テーマを解析して使い、子テーマ＋小さなカスタムプラグインで
拡張する**のを基本とする（親テーマの SEO・レスポンシブ・a11y の蓄積を活かし、更新にも壊されない）。

- 子テーマ: デザイントークン（Claude Design 由来）の反映、テンプレート断片の上書き
- カスタムプラグイン: 診断ツール埋め込み・ショートコード・REST 拡張
- Gutenberg カスタムブロック: 記事内で再利用する図解・CTA・診断パーツ
- カスタム投稿タイプ: コンテンツ資産の構造化（事例・用語集など）
- テーマ解析結果（構造・フック・スタイル体系）は攻略地図として DB に残す

### ダッシュボード — HTML 主・スプレッドシート従

分析ダッシュボードは **SQLite から Python で HTML を自動生成**するのを主とする（完全自動・証跡化可能）。
Notion HQ には数値サマリの書き戻しと HTML ダッシュボードの埋め込みのみ（Notion のチャートは使わない）。
従として、人が手でピボット探索したいとき用に**計測時系列を xlsx でエクスポート**できるようにし、
ブラウザ経由でスプレッドシートへ投入する（F3 で実装）。

### 計測データの取り込み — ブラウザエクスポート → 解体 → SQLite

GA4・Google タグマネージャ・Search Console などの計測系は **API 連携しない**（設定・認証・クォータが面倒で
保守負担になる）。代わりに**ブラウザ自動化で管理画面から Excel/CSV をエクスポートし、パースして SQLite の
計測時系列へ投入する**。取得スクショとエクスポートファイルのハッシュを証跡として残す。
SNS のインプレッション等も同様にブラウザ経由で取得 — 計測もすべて「ブラウザで突破」に統一。

### SNS 運用 — ブラウザで突破

SNS（X / note / Instagram / YouTube …）の投稿・計測は **API 契約ではなくブラウザ自動化で行う**
（TAKUMI の「実ブラウザで計測し、証跡を残す」路線の継承）。
公式 API の課金・審査・レート制約に依存しない。攻略したサイト構造は地図として DB に残し、次回実行を速くする。
スクリーンショット・公開 URL をブラウザ経由で取得し、そのまま証跡にする。

### 新規（HELIX 流）

1. 証跡ゲート（P1）とハーネス DB（KPI ツリー・施策・証跡・実測）
2. 二重ループの状態機械（P2）— どのスプリントの、どのステップに、何が滞留しているかを機械が把握
3. HELIX 式の開発統制（Forward/Reverse、V-pair、trace、証跡 gate）。製品コードや runtime workspace を
   HELIX 本体へ import する互換層は持たない
4. 外部基盤コネクタ — WordPress（REST API + WP-CLI。内部構築含む）と Notion（MCP）への読み書き。証跡・判定はハーネス DB 側に持つ

### 非スコープ

- 広告運用（変数として 0 に固定）
- 人間チームの staffing／velocity 管理（replenishment・review・retrospective は system/AI が Kanban を
  継続運転する cadence としてスコープ内。人間は別途定義された承認・判断 gate だけに関与する）
- HELIX 本体（開発ハーネス）の変更

## §7 進め方 — HELIX V-model × スライス駆動

本ハーネスの構築は HELIX の V-model（要求↔検証、設計↔テスト、実装↔単体テスト）を開発の背骨とする。
その各層を一括凍結してから次層へ進むのではなく、**各スライス = 端から端まで検証可能なインクリメント**として
必要な層を Forward で降り、検証結果を Reverse で上位へ還流する。
TAKUMI スキルや接続・パイプラインは各スライスが必要とした時点で引き込む（先行一括移植をしない）。
ドキュメントも「共通の背骨（スキーマ群・接続原則）＋スライスごとの要求」の形を取る。
本チャーターは層外の anchor（HELIX の L0 と同じ位置づけ）。

| スライス | 一気通貫で通すもの | 完了条件（動くインクリメント） |
|---|---|---|
| S0 ウォーキングスケルトン | ブログ記事 1 本: Notion ネタ → ワークスペース制作 → 審査 PASS → WP 公開 → 計測取得 → SQLite 証跡 | ペアゲート最小版込みで 1 本が証跡付きで公開される |
| S1 ループを閉じる | 計画↔計測ペア成立 → スプリントレビュー → 学習の上位還流 | 実測を入力に行動計画が 1 回更新される |
| S2 ヒアリングエンジン最小版 | 事業前提スキーマの不足検出 → 問診 → 充填 | 事業前提が型経由で確定し KPI ツリー初期形が起草される |
| S3+ 媒体・能力の逐次追加 | 媒体 1 つ or パイプライン 1 本ずつ（X、Podcast、診断ツール、…） | 各スライスごとに新しい面が証跡付きで稼働 |

スライスの順序・粒度は、HELIX の trace と検証クロージャーを壊さない範囲で、各開発イテレーションのレビューにより決める。

## §8 構成境界

### 開発リポジトリ

HELIX の成果物階層・正本／生成 view・検証ペアを、このリポジトリ内で完結させる。HELIX 本体の
source tree や runtime state へ本製品を配置しない。

```text
HELIX-MARKETING-HARNESS/
├── docs/                   # 00-authority + L0〜L6 の正本・生成 view・検証設計
├── src/helix/              # 本製品の Python semantic core（実装時）
├── tests/                  # gate／unit tests
├── tools/gates/            # 工程別の機械 gate
└── scripts/                # view 生成・検証用の薄い entrypoint
```

### runtime managed workspace（複数 domain）

物理 workspace は `business_profile` と `bounded_domain` の二段境界を必須とする。下記の
`<workspace-root>` は設定された managed root であり、リポジトリ root・HELIX 本体・任意の絶対 path を
既定値にしてはならない。directory 名に媒体名を焼き付けず、実媒体は domain manifest が参照する
版付き `media_binding` で追加・pause・retire・replacement する。

```text
<workspace-root>/
└── profiles/
    └── <business_profile_id>/
        ├── profile-manifest.json
        └── domains/
            └── <bounded_domain_id>/
                ├── domain-manifest.json
                ├── strategy/
                ├── backlog/
                ├── work/
                │   ├── drafts/
                │   └── assets-src/
                ├── evidence/
                └── exports/
```

- registry の canonical root と manifest の ID・version・root は一致させる。
- すべての read/write は profile ID と domain ID を要求し、path traversal、symlink escape、他境界との
  root overlap、archived domain への write を fail-close で拒否する。
- domain 間の共有は明示された export/import 契約だけで行い、相対 path や共通 directory による暗黙共有を禁止する。
- `strategy/` は上流戦略の投影、`backlog/` と `work/` は下流 Kanban の作業面、`evidence/` は検証証跡、
  `exports/` は境界外へ渡す不変成果物とし、互いの責務を混在させない。
- ID・状態・版・拒否条件の L3 正本は
  [FR-17／FR-35／FR-48 契約](../../L3-system-requirements/canonical/functional/fr-contracts.json) と
  [要件一覧](../../L3-system-requirements/canonical/functional/requirements_v0.1.md) とする。

### 保留（検討済み・現段階で不採用）

- **Shopify**: 月額固定費が原則に反し、自社販売は Stripe+WP で充足。本格 EC 化の際に再検討
- **メルカリ**: 物販の物理オペ（在庫・発送）が自走モデル外。デジタル販売は規約上不可。物販開始時に再訪
- **iOS App Store / Voicy**: 各項に記載のとおり条件付き保留

## §10 確定事項

- **Notion 構造（⑦ 確定 2026-07-30）**: 専用のフリー Notion ワークスペースを使用。
  構造設計は AI が実施済み — HQ ページ配下に 📋 行動計画 / 💡 ネタ帳（編集カレンダー・制作ボード付き）/
  🏃 スプリントバックログ（スプリントボード付き）の 3 DB をリレーション接続で構築（2026-07-30）。
- **SNS 接続方式（確定 2026-07-30）**: API ではなく**ブラウザ自動化で突破**。サイト構造の攻略地図を DB に蓄積。
- **TAKUMI 継承方針（確定 2026-07-30、2026-08-05 語義是正）**: そのまま移植ではなく、スキル・
  ワークフロー・タスクを素材として取り出す。開発は HELIX 式 V-model に従い、製品 runtime は
  Kanban-first + Scrum cadence として再配置する。
- **コマンド体系（② 確定 2026-07-30）**: **専用コマンドは持たない**。ハーネスの状態機械が次アクションを

  TAKUMI のコマンド群・「匠」の呼称・文言は一切継承しない（機能素材のみ取り込む）。
- **通知・承認（確定 2026-07-30）**: **Claude Code アプリのプッシュ通知**で行う。専用チャネルは持たない。
- **Discord = コミュニティマーケティング媒体（確定 2026-07-30）**: 通知面ではなく**運用対象の媒体**として扱う。
  自前コミュニティの構築・運営（コミュニティマーケティング）を下位ループの媒体の一つに加え、
  投稿・応答・活性度計測を他媒体と同じくループで回す（証跡・KPI も同様に SQLite へ）。
- **公開承認（④ 確定 2026-07-30）**: 公開直前に**スマホ連携（プッシュ通知）で束縛承認**。
  安定稼働の実績（証跡ベース）が積み上がったら**オートモードへ段階移行**し、人の承認なしで公開まで自走。
- **ライセンス（⑤ 確定 2026-07-30）**: 現段階では設定しない。公開配布を決める時点で再検討。
- **ハーネス DB（確定 2026-07-30）**: **SQLite** を採用し、**数値・状態管理に限定**（KPI ツリー・施策状態・計測時系列・ペア成立判定・証跡参照）。
  画像・動画など重いコンテンツ実体は WordPress（メディアライブラリ）に保管し、SQLite からは URL/ID 参照のみ。
  Notion は人が触る計画・ネタ・カレンダーの UI に限定し、同期は低頻度（スプリント開始時の読取り／レビュー成立時の書戻し）。
  高頻度の読み書きはすべて SQLite 側に寄せる。
- **時間軸・サイクル（① 確定 2026-07-30）**: ブランド計画は **1 年**で立てる（コンテンツが花開く期間）。
  サイクルは**媒体単位（下位）とブランドの成長（上位）で分離**し、暦ではなく対象に従って回す。
  将来的に MMM 的な全体計測（オーガニック版）と紐づける — P3 に記載。
- **実装言語（③ 確定 2026-07-30）**: ハーネス本体（状態機械・ゲート判定・KPI ツリー DB・意味判断）は **Python**。
  データと意味を扱う中核であり、HELIX 本体の「Python = semantic core」方針とも一致する。
  WordPress 側の構築・カスタマイズでは **PHP / HTML / CSS / JavaScript** を扱う（テーマ・プラグイン・LP 等）。
