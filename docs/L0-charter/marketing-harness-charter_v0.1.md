## 1. 一言で

**TAKUMI-CMO のマーケティング頭脳を、HELIX 流の「機械で品質を守るハーネス」に載せ替える。**

TAKUMI は「ゼロ広告費・コンテンツとブランディングで成果を納品する CMO プラグイン」として完成度が高い。
一方 HELIX の思想は「AI の『完了しました』を宣言でなく、テスト・証跡・機械ゲートで殴り返す」こと。
本プロジェクトはこの二つを掛け合わせ、**マーケティング施策の企画〜実行〜計測を、証跡ゲート付きで
AI に自走させるハーネス**を作る。

## 2. なぜ作るか（課題）

1. **TAKUMI は「プラグイン」であって「ハーネス」ではない** — スキル・手順書は豊富だが、
   成果物の品質保証は審査エージェント（design-critic 等）のプロンプト頼み。機械ゲート・証跡 DB がない。
2. **マーケ成果物は「完了しました」詐欺が最も起きやすい領域** — 記事を書いた／投稿した／計測した、の
   宣言はコード以上に検証されにくい。公開 URL・計測値・スクリーンショット等の**証跡必須化**が要る。
3. **HELIX 本体は開発（コード）特化** — マーケ領域へ横展開するには、V-model 的な
   「企画↔検証」対応構造をマーケ用に再定義する必要がある。

## 3. 何を作るか（スコープ）

### 継承するもの（TAKUMI から）

| 資産 | 内容 | 扱い |
|---|---|---|
| skills/（約40本） | seo-jp, copywriting, stp-jp, kpi-design-jp など | ほぼそのまま移植。命名・frontmatter を統一 |
| agents/（10本） | cmo-strategist, design-critic, outcome-verifier など | 役割を維持しつつ、判定をゲート連携に変更 |
| commands/（匠◯◯） | /匠戦略 /匠発信 /匠計測 など | エントリポイントとして継承（名称は要検討） |
| procedures/ | takumi-* 手順書群 | ハーネスの「駆動モデル」定義に昇格 |
| ゼロ広告費ゲート | 有料指標・広告遷移の遮断 | **機械的制約として維持**（本ハーネスの独自性） |
| ∞ループ | 上流（戦略）×下流（実行）を KPI ツリーで接続 | ハーネスの状態機械として実装 |

### 新規に作るもの（HELIX 流）

1. **証跡ゲート** — 施策は「公開 URL / 計測スナップショット / 審査 PASS 記録」が揃うまで
   完了扱いにならない。宣言ベースの完了を構造的に禁止。
2. **マーケ版 V-model** — 上流の各層（戦略→KPI→企画→制作）に対応する検証層
   （成果検証→KPI 実測→企画レビュー→品質審査）をペアで定義。
3. **ハーネス DB** — KPI ツリー・施策・証跡・実測値を保持し、∞ループの往復を機械的に駆動。
4. **HELIX ローダ互換** — HELIX 本体から `@...` import で読める構成（グローバル CLAUDE.md の方針に従う）。

### 非スコープ

- 広告運用（TAKUMI 同様、変数として 0 に固定）
- 人間チーム運用（velocity / sprint ceremony）
- HELIX 本体（開発ハーネス）の変更

## 4. 柱（P0–P5 案）

- **P0 ゼロ広告費ゲート** — 有料経路の機械遮断（TAKUMI 継承・最優先で維持）
- **P1 証跡必須の完了判定** — 公開 URL・計測値・審査記録なしに done にならない
- **P2 マーケ V-model** — 戦略〜制作の各層に検証層をペアリング
- **P3 KPI ツリー駆動** — DB 上の KPI ツリーが上流・下流ループの背骨
- **P4 エージェント分業** — strategist / writer / critic / verifier の分離と相互監査
- **P5 倫理線** — 心理学は不安の解消に使い増幅に使わない（TAKUMI の線を機械側でも保持）

## 5. 進め方（フェーズ）
